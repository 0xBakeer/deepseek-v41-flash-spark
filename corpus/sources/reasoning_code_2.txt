A recursive `DeepPartial<T>` fixes the type and breaks the implementation instead -- the spread replaces `editor` wholesale, so `fontSize` arrives and `tabSize` disappears. Type and code have to change together.

So `DeepPartial<T>` mapped recursively over `T[K] extends object`, plus a merge that recurses on plain objects and assigns everything else.

Arrays must not merge element-wise: `excludePaths: ['dist']` means that list, not the defaults plus one. `Array.isArray` makes them leaves.

Recursive type, matching recursive merge, arrays treated as leaves.
=== ANSWER
```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends readonly unknown[] ? T[K]
    : T[K] extends object ? DeepPartial<T[K]>
    : T[K];
};

const isPlain = (v: unknown): v is Record<string, unknown> =>
  typeof v === 'object' && v !== null && !Array.isArray(v);

export function merge<T extends object>(base: T, over: DeepPartial<T>): T {
  const out: Record<string, unknown> = { ...base };
  for (const [k, v] of Object.entries(over)) {
    const prev = out[k];
    out[k] = isPlain(prev) && isPlain(v) ? merge(prev, v as never) : v;
  }
  return out as T;
}
```

`pool.map` is shorter but yields in submission order and raises on the first failure; `as_completed` over a future-to-url dict keeps every outcome.

`fut.result()` re-raises whatever the worker raised, so `probe` must catch `URLError` itself and return a `statusCode` of 0. `HTTPError` is a response, so a 404 is a real `statusCode`.

Threads for I/O, every outcome collected, `statusCode` defined even on failure.
=== ANSWER
```python
import urllib.error, urllib.request
from concurrent.futures import ThreadPoolExecutor, as_completed

def probe(url, timeout=5):
    req = urllib.request.Request(url, method="HEAD")
    try:
        with urllib.request.urlopen(req, timeout=timeout) as resp:
            return resp.status
    except urllib.error.HTTPError as exc:
        return exc.code
    except (urllib.error.URLError, OSError):
        return 0

def check_all(urls, workers=8):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(probe, u): u for u in urls}
        for fut in as_completed(futures):
            out[futures[fut]] = {"statusCode": fut.result()}
    return out
```

=== PROMPT
Type a lookup table so the keys are checked and the values are inferred, in TypeScript.
=== THINK
`const ROUTES: Record<string, string>` widens every key to `string`, so a typo at the call site compiles. `as const` keeps the literal keys and values.

```ts
const ROUTES = {
  home: '/',
  settings: '/settings',
} as const;

```
`keyof typeof ROUTES` is the whole trick: `typeof` recovers the inferred object type and `keyof` narrows it to `'home' | 'settings'`, which `pathFor` then enforces on its parameter.

`as const` also makes the values `readonly`, so a later assignment is a compile error rather than a runtime surprise.

I wanted a type annotation on `ROUTES` for documentation -- that defeats the inference, since annotating widens it back. `satisfies` gives the check without the widening, which is the pair I want.

Reverse lookup needs `Object.entries`, and `Object.entries` types the keys as `string`, so one cast at that boundary and `pathFor` stays clean.

Literal inference kept, keys checked by `keyof typeof`, `satisfies` in place of an annotation.
=== ANSWER
```ts
export const ROUTES = {
  home: '/',
  settings: '/settings',
  billing: '/settings/billing',
} as const satisfies Record<string, `/${string}`>;

export type RouteName = keyof typeof ROUTES;
export type RoutePath = (typeof ROUTES)[RouteName];

export function pathFor(name: RouteName): RoutePath {
  return ROUTES[name];
}

export function nameFor(path: string): RouteName | undefined {
  const entries = Object.entries(ROUTES) as [RouteName, RoutePath][];
  return entries.find(([, p]) => p === path)?.[0];
}
```
